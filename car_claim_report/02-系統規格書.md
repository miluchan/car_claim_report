# 汽車險理賠系統（事故報案處理）— 系統規格書

版本：v1.0　　最後更新：依本次對話所完成之全部功能整理

---

## 一、系統概述

本系統為汽車險事故報案與理賠處理系統，供經辦人員於客戶報案時，查詢投保狀態、建立理賠案件、蒐集事故相關資料、處理文件簽署與估價，並支援客戶端自助拍照與遠端簽署。

**設計原則**：
- 投保資料（保單）不重複建立，理賠系統直接查詢既有車險報價系統的資料庫，僅在立案當下拍攝一份快照存入理賠案件，之後保單異動不影響已受理案件。
- 所有金額/期限相關的業務規則採規則式（非AI）判斷，確保決策透明可解釋。
- 影像辨識（AI文件辨識）介面已預留，實際辨識邏輯尚未串接，屬於未來擴充項目。

## 二、技術架構

| 項目 | 內容 |
|---|---|
| 前端框架 | React（單一 App.js 元件） |
| 樣式 | Bootstrap 5 |
| 後端／資料庫 | Supabase（PostgreSQL + 匿名金鑰存取，無登入系統） |
| 資料庫部署位置 | 沿用既有車險報價系統的 Supabase 專案（該專案已規劃轉型為理賠系統資料庫） |
| 部署平台 | Vercel（Root Directory 需指向實際程式碼所在子目錄） |
| 檔案儲存 | 目前為前端暫存（`URL.createObjectURL`），**尚未接上正式雲端檔案儲存**，屬已知待辦事項 |
| 身分驗證 | 無登入系統；OTP身分驗證為模擬（產生亂數驗證碼並用alert顯示，非真實簡訊平台） |
| 客戶自助管道 | 簡訊／LINE 為半自動（開啟手機App並帶入內容，仍需使用者手動按送出），非真正自動發送 |

## 三、主要畫面與功能規格

### 0. 主畫面查詢區

| 功能 | 規格 |
|---|---|
| 受理與查詢報案 | 輸入車號，查詢 `quote_full_records` 中該車**最新一筆「已出單」**的投保紀錄（非單純抓最新一筆，避免誤判到未出單或已被取代的舊紀錄） |
| 受理判斷 | 需同時滿足：①在強制險／任意險有效期間內　②`payment_status = 已出單`。任一不成立即紅燈拒絕受理，且不會帶出投保內容 |
| 立案編號 | 格式 `yyyymmdd-001`，受理當下即寫入資料庫（非等按「儲存」才產生），並用資料庫唯一索引防止同車號同時間被兩人各自建立案件 |
| 通報時間 | 受理當下鎖定寫入，其後任何「儲存」動作皆不會覆蓋此欄位 |
| 未結案續處理 | 若該車號已有「未結案且未註銷」的案件，直接帶出該案件完整進度，不重新產生新編號，也不彈出額外提示 |
| 投保內容 | 顯示保單投保代號、險種、保額（非保費）；受理未通過時此按鈕不可用 |
| AI引導事故現場處理 | 依序引導8個拍攝角度（事故全景→碰撞位置→本車受損→對方車輛→對方車牌→行照／駕照→道路標線號誌→其他證據），每步可連續拍攝多張，另提供「即拍即傳」不指定項目的快速拍攝入口 |
| 報案人電話／簡訊通知／LINE通知 | 產生帶 `?guideClaimId=` 參數的連結，供客戶自助完成拍照 |
| 未決案查詢 | 開啟即列出所有「未結案且未註銷」案件一覽表，可用車號／立案編號篩選；「詳細內容」為**唯讀檢視**，不會將該案帶入可編輯狀態 |
| 註銷立案 | 標記 `voided = true`，不刪除任何資料；註銷後該車號視為釋出，可重新受理新案件 |
| 案件處理進度 | 已立案→文件完備→已預估→已結案→已付款，五階段燈號顯示，未達成為灰燈、達成為綠燈 |

### 1～2. 被保險人／駕駛人區塊

- 被保險人資料自投保紀錄快照帶入，可手動修正。
- 駕駛人提供「同被保險人」一鍵帶入按鈕。

### 3. 對方車及事故狀況

- 一案可登記多台對方車，各自獨立記錄受傷／送醫／拖吊／本車維修／可否行駛等狀況。
- 事故時間、地點、報警狀況、警方單位為**案件層級**欄位（非個別對方車各自登記）。
- 「X」為暫時隱藏（資料保留，可用「新增」依後進先出順序復原）；另有獨立的「刪除」按鈕可真正移除該筆資料，刪除前需二次確認。
- 儲存時會自動過濾完全空白的對方車列，不會存入無意義的空資料。

### 4. 事故處理

- 上傳文件、即拍即傳（直接開啟相機）、上傳文件調閱、AI文件辨識（介面已建置，辨識邏輯待串接）。

### 5. 文件線上簽署

- 文件類型：理賠申請書／和解書，畫面內容依實際官方文件格式呈現核定明細。
- 流程：文件內容 → OTP身分驗證＋注意事項 → 手寫簽名。
- 已簽署之文件類型不可重複簽署（直接提示並阻擋，不再詢問是否重簽）。
- 提供遠端簽署（簡訊／LINE），連結導向獨立的客戶簽署頁面（`?signClaimId=&signDocType=`），該頁面同樣會檢查是否已簽署。

### 6. 修車估價

- 上傳文件、上傳文件調閱、AI文件辨識（同事故處理，共用底層邏輯）。
- 應備文件清單：多選欲納入本案的文件項目，各自打勾核對，整體以紅綠燈顯示是否備齊。
- 預估理賠金額欄位，供案件分流規則使用。

### 8. 案件分流

- 規則：有人員受傷 → 高複雜度；金額 ≤ 3萬元 → 低複雜度；其餘 → 中複雜度。
- 系統自動判斷並亮燈建議，經辦人員可手動點選其他選項覆蓋，並記錄是否為人工覆蓋。

### 結案

- 需先填妥「決算金額」（與預估金額為不同欄位）才能進行結案。
- 結案按鈕會再次跳出確認對話框，確認後才真正寫入結案狀態並清空畫面；取消則不影響現有資料與進度。

## 四、關鍵業務規則彙整

| 規則 | 說明 |
|---|---|
| 受理判斷 | 保單需在有效期間內，且必須為「已出單」狀態，僅有到期日符合、但尚未出單者不予受理 |
| 立案編號唯一性 | 以資料庫寫入時的重試機制確保同一天內編號不重複 |
| 同車號防重複受理 | 資料庫層級的部分唯一索引（`plate_no` 於 `case_closed=false and voided=false` 條件下唯一），確保同一台車不會同時存在兩筆進行中案件 |
| 樂觀鎖（防止資料互相覆蓋） | 每筆案件皆有 `updated_at`；儲存前會重新比對資料庫目前版本與畫面讀取時的版本，若不一致則擋下儲存，提示使用者重新查詢取得最新版本後再處理，避免後儲存者悄悄覆蓋先儲存者的修改 |
| 結案前置條件 | 必須填寫決算金額；結案動作需二次確認（Y/N），確認前的所有操作（含填寫金額）皆不視為結案 |
| 案件分流 | 純規則式判斷（金額門檻＋受傷旗標），不使用AI，確保決策可解釋、可稽核 |

## 五、已知限制與未來待辦事項

1. **檔案儲存**：目前上傳文件僅存於瀏覽器本地暫存網址，重新整理或跨裝置無法保留實際檔案內容，需另外串接正式雲端物件儲存（如 Supabase Storage）。
2. **AI文件辨識**：介面與資料欄位（`ai_recognition_result`）已就緒，尚未串接真實影像辨識服務，需申請並整合影像AI服務後才能實際運作。
3. **簡訊／LINE通知**：目前為半自動（開啟裝置本身的App並帶入內容，仍需人工按送出），若需全自動發送，須另外申請簡訊閘道商帳號並整合API。
4. **併發編輯保護**：目前以樂觀鎖（版本比對）擋下衝突儲存，但無法得知「是誰」正在編輯（系統無登入身分機制）。如需更完整的協作機制（即時顯示他人正在編輯、鎖定畫面等），需另行規劃登入身分系統。
5. **案件狀態欄位（`claims.status`）**：目前保留供未來流程擴充，尚未實際串接完整狀態機。
