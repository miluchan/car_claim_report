# 汽車險理賠系統（事故報案處理）— 系統規格書

版本：v2.0　　涵蓋自受理判斷修正到自製相機、真實檔案儲存、樂觀鎖等所有後續迭代

---

## 一、系統概述

本系統為汽車險事故報案與理賠處理系統，供經辦人員於客戶報案時，查詢投保狀態、建立理賠案件、蒐集事故相關資料、處理文件簽署與估價，並支援客戶端自助拍照與遠端簽署。

**設計原則**：
- 投保資料（保單）不重複建立，理賠系統直接查詢既有車險報價系統的資料庫，僅在立案當下拍攝一份快照存入理賠案件；被保險人資料為唯讀，不可事後修改。
- 所有金額/期限相關的業務規則採規則式（非AI）判斷，確保決策透明可解釋。
- 檔案（照片、影片、文件）內容直接存進資料庫本身，不依賴瀏覽器本地暫存，確保跨裝置、跨瀏覽器都能正確存取。
- 影像辨識（AI文件辨識）介面已預留，實際辨識邏輯尚未串接，屬於未來擴充項目。

## 二、技術架構

| 項目 | 內容 |
|---|---|
| 前端框架 | React（單一 App.js 元件） |
| 樣式 | Bootstrap 5 |
| 後端／資料庫 | Supabase（PostgreSQL + 匿名金鑰存取，無登入系統） |
| 資料庫部署位置 | 沿用既有車險報價系統的 Supabase 專案 |
| 部署平台 | Vercel（Root Directory 需指向實際程式碼所在子目錄） |
| 檔案儲存 | **v2.0：直接以base64編碼存入 `claim_documents.file_data` 欄位**，圖片自動壓縮（最長邊≤1600px，轉JPEG）；不依賴外部雲端儲存服務，量大後可評估改接 Supabase Storage |
| 相機／錄影 | **v2.0新增：自製相機介面**，以 `getUserMedia` 取得即時預覽、`MediaRecorder` 錄影（上限15秒），取代原生檔案選擇器的相機模式 |
| 身分驗證 | 無登入系統；OTP身分驗證為模擬（產生亂數驗證碼並用alert顯示，非真實簡訊平台） |
| 客戶自助管道 | 簡訊／LINE 為半自動（開啟手機App並帶入內容，仍需使用者手動按送出） |

## 三、主要畫面與功能規格

### 0. 主畫面查詢區

| 功能 | 規格 |
|---|---|
| 受理與查詢報案 | 查詢 `quote_full_records` 中該車**所有紀錄**，優先取 `payment_status=已出單` 的那一筆（而非單純取最新一筆，避免誤判到未出單或已被取代的舊紀錄） |
| 受理判斷 | 需同時滿足：①在強制險／任意險有效期間內　②`payment_status = 已出單`。任一不成立即紅燈拒絕受理，**不設定投保內容資料**（v2.0修正） |
| 立案編號 | **v2.0：受理成功當下立即寫入資料庫**，透過重試機制確保同日內編號不重複；同一車號若已有未結案案件，會被資料庫唯一索引擋下，自動改為帶出既有那一筆 |
| 通報時間 | 立案當下鎖定寫入，其後任何「儲存」動作皆不會覆蓋此欄位 |
| 未結案續處理 | 若該車號已有「未結案且未註銷」的案件，直接帶出該案件完整進度，不重新產生新編號、不彈出提示 |
| 未決案查詢 | 開啟即列出所有「未結案且未註銷」案件一覽表，可用車號／立案編號篩選；「詳細內容」為**唯讀檢視**，不會將該案帶入可編輯狀態 |
| 註銷立案 | 標記 `voided = true`，不刪除資料，註銷後該車號視為釋出，可重新受理新報案 |
| 案件處理進度 | 已立案→文件完備→已預估→已結案→已付款，五階段燈號顯示 |

### 1～2. 被保險人／駕駛人區塊

- **v2.0：被保險人資料全部改為唯讀**，投保快照不可事後修改，畫面上明確標示「投保資料快照，不可修改」。
- 駕駛人提供「同被保險人」一鍵帶入按鈕。

### 3. 對方車及事故狀況

- 一案可登記多台對方車，各自獨立記錄受傷／送醫／拖吊／本車維修／可否行駛等狀況。
- 事故時間、地點、報警狀況、警方單位為**案件層級**欄位（非個別對方車各自登記）。
- 「X」為暫時隱藏（資料保留，可用「新增」依後進先出順序復原）；另有獨立「刪除」按鈕可真正移除，刪除前需二次確認。
- **v2.0修正**：對方車編號改為依畫面現有資料動態計算，避免編號因React重複渲染而不規則跳號。
- 儲存時自動過濾完全空白的對方車列。

### 4. 事故處理／6. 修車估價

- **上傳文件**：一般檔案選擇器（不限類型），適合上傳已存在手機裡的既有照片或檔案；此入口在手機瀏覽器仍可能出現系統原生拍照選項，無法透過網頁程式完全排除，已於畫面加上引導文字建議改用「即拍即傳」。
- **即拍即傳**：**v2.0新增，兩區塊皆有**，開啟自製相機介面，快門立即存檔，可額外錄影（上限15秒）。
- **AI引導事故現場處理**（僅事故處理區塊）：依序引導8個拍攝角度，每步驟皆可開啟自製相機拍照或錄影，不限張數，直到按「下一步」才前進；另有不指定項目的「即拍即傳」快速入口。
- **上傳文件調閱**：圖片顯示縮圖、影片可播放、HEIC格式顯示提示與下載連結、其他類型（PDF/文件）顯示下載連結。**v2.0新增**：每筆文件皆可按「刪除」，二次確認後自資料庫真正刪除。
- **AI文件辨識**：介面已建置，尚未串接真實辨識服務。
- **應備文件清單**（修車估價）：多選欲納入本案的文件項目，各自打勾核對，整體以紅綠燈顯示是否備齊。

### 5. 文件線上簽署

- 文件類型：理賠申請書／和解書，畫面內容依實際官方文件格式呈現核定明細。
- 流程：文件內容 → OTP身分驗證＋注意事項 → 手寫簽名。
- 已簽署之文件類型**直接阻擋重複簽署**（不再詢問是否要重簽）。
- **v2.0修正**：簽名畫布觸點偏移問題（內部繪圖解析度與CSS顯示尺寸不一致所致）已修正；簽署畫面顯示期間會鎖定整個頁面捲動，避免手機簽名時畫面跟著滑動。
- 提供遠端簽署（簡訊／LINE），連結導向獨立客戶簽署頁面（`?signClaimId=&signDocType=`），同樣會檢查是否已簽署。

### 結案

- 需先填妥「決算金額」（與預估金額為不同欄位）才能進行結案。
- 結案按鈕會再次跳出確認對話框，確認後才真正寫入結案狀態並清空畫面。

### 儲存立案資料

- **v2.0變更**：每次成功儲存後，畫面會清空。要繼續處理同一筆案件，需重新用「受理與查詢報案」查詢該車號，系統會自動帶回目前進度。

## 四、關鍵業務規則彙整

| 規則 | 說明 |
|---|---|
| 受理判斷 | 保單需在有效期間內，且必須為「已出單」狀態，優先比對已出單紀錄而非單純取最新一筆 |
| 立案編號唯一性 | 受理當下即寫入資料庫，透過重試機制確保同一天內編號不重複 |
| 同車號防重複受理 | 資料庫層級的部分唯一索引（`plate_no` 於 `case_closed=false and voided=false` 條件下唯一） |
| 樂觀鎖（防止資料互相覆蓋） | 每筆案件皆有 `updated_at`；儲存前重新比對資料庫目前版本與畫面讀取時的版本，不一致則擋下儲存並提示重新查詢 |
| 結案前置條件 | 必須填寫決算金額；結案動作需二次確認（Y/N） |
| 案件分流 | 純規則式判斷（金額門檻＋受傷旗標），不使用AI，確保決策可解釋、可稽核 |
| 檔案儲存 | 內容以base64直接存入資料庫；圖片自動壓縮；圖片格式判斷結合MIME類型與副檔名雙重確認，避免手機環境下MIME類型缺失導致誤判 |
| 文件刪除 | 二次確認後自資料庫實際刪除，不佔用儲存空間 |

## 五、已知限制與未來待辦事項

1. **檔案儲存規模**：目前以base64直接存入資料庫欄位，適合現階段資料量；若檔案數量或容量大幅成長，建議改接 Supabase Storage 等正式雲端物件儲存服務。
2. **AI文件辨識**：介面與資料欄位（`ai_recognition_result`）已就緒，尚未串接真實影像辨識服務。
3. **簡訊／LINE通知**：目前為半自動，全自動發送須另申請簡訊閘道商帳號並整合API。
4. **併發編輯保護**：以樂觀鎖擋下衝突儲存，但因系統無登入身分機制，無法得知「是誰」正在編輯，僅能偵測「是否已被改過」。
5. **手機瀏覽器原生選單**：一般「上傳文件」入口因瀏覽器機制限制，仍可能顯示系統原生拍照選項，無法透過網頁程式完全排除。
6. **HEIC格式**：iPhone原始照片格式部分瀏覽器無法直接預覽，系統會保留完整檔案內容並提供下載，但無法保證所有裝置都能直接開啟。
